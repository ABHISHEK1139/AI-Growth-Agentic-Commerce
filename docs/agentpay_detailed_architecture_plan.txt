AGENTPAY
Complete Production-Grade Architecture and Phase-by-Phase Implementation Plan
AI-Native Merchant Gateway for Agentic Commerce

Version: 1.0
Prepared: 21 August 2026

======================================================================
1. DOCUMENT PURPOSE
======================================================================

This document converts the AgentPay concept into a practical product-development plan. It is written as an implementation blueprint for a student or small engineering team building a credible Razorpay Track 01 submission.

AgentPay is not primarily an AI shopping chatbot. It is a merchant-side AI commerce gateway. Its job is to make an ordinary merchant machine-readable and safely transactable by AI buyers.

The platform must support the following lifecycle:

USER INTENT
  -> STRUCTURED INTENT
  -> CATALOG DISCOVERY
  -> OFFER RETRIEVAL
  -> OFFER COMPARISON
  -> CHECKOUT CREATION
  -> DETERMINISTIC POLICY EVALUATION
  -> BUYER AUTHORIZATION
  -> PAYMENT CREATION
  -> PAYMENT VERIFICATION
  -> ORDER CONFIRMATION
  -> AUDIT AND NOTIFICATION

The central engineering principle is separation of concerns:

1. The language model interprets language and selects tools.
2. Deterministic services own prices, inventory, policies, authorization, and payment.
3. The payment provider owns payment execution and payment state.
4. The audit system records consequential actions.
5. Untrusted product and web content is treated as data, never as instructions.

This plan intentionally prioritizes a working transaction loop over a large frontend, excessive protocol implementation, or premature microservices.

======================================================================
2. PRODUCT DEFINITION
======================================================================

2.1 Product statement

AgentPay enables merchants to publish products, offers, policies, inventory, and checkout capabilities through machine-readable interfaces. AI buyers can discover products, compare offers, create checkouts, request authorization, and complete payments without the AI receiving unrestricted database or payment access.

2.2 Primary users

Merchant administrator:
- Imports and manages a catalog.
- Configures offers, inventory, delivery, returns, discounts, and AI purchasing rules.
- Reviews agent activity, failures, blocked actions, and transactions.

Buyer:
- Describes a need in natural language.
- Reviews structured product and offer recommendations.
- Approves an authorization or payment when required.
- Receives an explanation and transaction receipt.

AI buyer:
- Converts user language into a structured intent.
- Calls allowlisted commerce tools.
- Compares validated offers.
- Provides evidence-backed explanations.
- Never directly changes price, inventory, policy, authorization, or payment state.

Platform operator:
- Monitors system health, model usage, payment events, security events, and audit records.

2.3 MVP definition

The MVP is complete only when the following works end to end:

- One merchant.
- At least 100 usable products.
- A normalized catalog and offer model.
- Structured intent extraction.
- Deterministic product and offer filtering.
- Checkout creation.
- Spending and category policy evaluation.
- Buyer authorization.
- Razorpay test-mode order/payment flow.
- Payment verification.
- Idempotent retry behavior.
- Complete audit trail.
- One price-change or payment-timeout failure scenario.
- Merchant dashboard showing the transaction timeline.

The 20,000-product catalog, research agent, protocol adapters, dynamic UI, cross-sell, and campaign automation are later phases.

3. ARCHITECTURAL PRINCIPLES
======================================================================

3.1 Deterministic financial core

The LLM may propose an action but may not decide whether a financial action is permitted. The policy service must calculate the decision from explicit inputs and versioned rules.

3.2 Canonical internal model

External protocol formats should be translated into AgentPay's internal objects:

- Intent.
- Product.
- Offer.
- Checkout.
- Authorization.
- Payment.
- Order.
- Event.
- Evidence.

This prevents the project from becoming dependent on unstable external protocol details.

3.3 Explicit state transitions

A checkout, payment, and order must move through controlled states. Direct database updates from an agent endpoint are prohibited.

3.4 Server-side trust boundary

The browser and LLM are untrusted clients. Razorpay secrets, policy logic, payment verification, and order finalization remain server-side.

3.5 Untrusted content isolation

Product descriptions, reviews, merchant notes, web pages, and external documents can contain prompt injection. They must be passed to the model as quoted evidence with provenance and never as executable instructions.

3.6 Idempotent money mutations

Every money-mutating endpoint requires an idempotency key. A retry must return the original operation result rather than create a duplicate order or payment.

3.7 Observable by default

Every request, model run, tool call, policy decision, payment attempt, retry, and webhook must be traceable using request_id, trace_id, agent_run_id, checkout_id, payment_id, and order_id where available.

3.8 Modular monolith first

Begin with one FastAPI application organized into modules. Use PostgreSQL, Redis, and a worker process. Split into independent services only after the domain boundaries and traffic patterns are understood.

6. STATE MACHINES
======================================================================

6.1 Commerce transaction state machine

DISCOVERED
  -> OFFER_SELECTED
  -> CHECKOUT_CREATED
  -> POLICY_CHECKED
  -> AUTHORIZATION_PENDING
  -> AUTHORIZED
  -> PAYMENT_CREATED
  -> PAYMENT_PENDING
  -> PAYMENT_VERIFIED
  -> ORDER_CONFIRMED
  -> COMPLETED

Allowed failure states:
- PRICE_CHANGED.
- INVENTORY_CHANGED.
- CHECKOUT_EXPIRED.
- POLICY_BLOCKED.
- AUTHORIZATION_EXPIRED.
- PAYMENT_FAILED.
- PAYMENT_TIMEOUT.
- PAYMENT_UNKNOWN.
- CANCELLED.

6.2 Transition rules

- DISCOVERED -> OFFER_SELECTED only if the offer exists and is active.
- OFFER_SELECTED -> CHECKOUT_CREATED only after a fresh offer validation.
- CHECKOUT_CREATED -> POLICY_CHECKED only after total calculation on the server.
- POLICY_CHECKED -> AUTHORIZATION_PENDING if approval is needed.
- POLICY_CHECKED -> AUTHORIZED only when an existing authorization covers the checkout.
- AUTHORIZATION_PENDING -> AUTHORIZED only after explicit buyer approval.
- AUTHORIZED -> PAYMENT_CREATED only if checkout, authorization, and price hashes match.
- PAYMENT_CREATED -> PAYMENT_PENDING after provider order creation.
- PAYMENT_PENDING -> PAYMENT_VERIFIED only after provider verification or a trusted webhook.
- PAYMENT_VERIFIED -> ORDER_CONFIRMED only once.
- Any terminal state must reject duplicate finalization.

6.3 State transition implementation

Implement a transition function rather than allowing controllers to update status directly:

transition(transaction, event, context) -> new_state

The function checks:
- Current state.
- Permitted event.
- Required fields.
- Hash consistency.
- Authorization validity.
- Expiry.
- Actor permissions.

Persist both the new aggregate state and an audit event in one database transaction.

10. PHASE 2 — CATALOG INGESTION AND NORMALIZATION
======================================================================

Goal: transform an external dataset into reliable merchant-facing commerce data.

10.1 Ingestion stages

RAW IMPORT
  -> schema inspection
  -> field mapping
  -> category filtering
  -> record validation
  -> product deduplication
  -> variant extraction
  -> merchant assignment
  -> offer generation
  -> image processing
  -> embedding generation
  -> quality report
  -> publish

10.2 Raw versus processed data

Never modify raw files. Store them with:
- source name.
- download or acquisition date.
- checksum.
- schema version.
- license notes.
- processing run ID.

Processed records must include source provenance.

10.3 Data quality rules

Reject or flag products with:
- Missing title.
- Missing category.
- Invalid price.
- Negative inventory.
- Unsupported currency.
- Broken image URL.
- Duplicate external identifier.
- Unreasonably long description.
- Specification values with invalid units.

Normalize:
- Currency to minor units.
- Memory to GB.
- Storage to GB.
- Weight to grams.
- Dimensions to millimeters.
- Delivery to integer days.
- Boolean values to true/false.

10.4 Product deduplication

Use a layered approach:
- Exact external ID match.
- Normalized title and brand match.
- SKU match.
- Similarity candidate generation.
- Human review for uncertain pairs.

Do not merge products solely because their titles are similar. Product variants must remain distinct when specifications or price differ.

10.5 Catalog publishing

Use draft and published versions:
- Import creates a draft catalog version.
- Validation generates errors and warnings.
- Merchant reviews flagged records.
- Publish atomically switches the active version.
- Existing checkouts preserve their offer snapshots.

10.6 Scaling from 100 to 20,000 products

Start with 100 products that cover the demo scenario. Then add 1,000 products and measure query performance. Finally process the planned 20,000 products.

Suggested distribution:
- Laptops and computers: 4,000.
- Smartphones: 2,500.
- Monitors: 2,000.
- Audio: 2,000.
- Computer accessories: 2,500.
- Cameras: 1,500.
- Home electronics: 2,000.
- Appliances: 2,000.
- Other electronics: 1,500.

This distribution is a planning target, not a requirement.

10.7 Images

Images are presentation assets, not the source of financial truth. Store:
- Product ID.
- Image type.
- Original URL.
- Object storage key.
- Width and height.
- Content hash.
- Download status.

Respect dataset licensing and source terms. For a submission, document whether images are used only for demonstration.

10.8 Catalog APIs

Internal service methods:
- import_catalog(source, run_id).
- validate_product(product).
- normalize_product(record).
- publish_catalog(version_id).
- get_catalog_health(merchant_id).

Admin endpoints:
- POST /api/v1/catalog/import.
- GET /api/v1/catalog/imports/{run_id}.
- GET /api/v1/catalog/health.
- POST /api/v1/catalog/publish.

11. PHASE 3 — CATALOG SEARCH AND OFFER ENGINE
======================================================================

Goal: return valid offers without allowing the LLM to invent commerce facts.

11.1 Two-stage retrieval

Stage A: deterministic filtering.
- Category.
- Price ceiling.
- RAM minimum.
- Storage minimum.
- Delivery maximum.
- Inventory greater than zero.
- Merchant and policy constraints.

Stage B: ranking.
- Price fit.
- Specification fit.
- Delivery fit.
- Return policy.
- Semantic relevance.
- Merchant-defined ranking.

11.2 Search response contract

Return a bounded candidate set, for example 5 to 20 offers. Each result should include only fields necessary for reasoning:
- offer_id.
- product_id.
- title.
- key specifications.
- price.
- inventory status.
- delivery estimate.
- return summary.
- evidence references.
- offer expiry.

11.3 Semantic search

Use embeddings for descriptions, features, use cases, and compatibility text. Do not use semantic search to decide price, inventory, or authorization eligibility.

Query flow:
1. Extract structured constraints.
2. Apply SQL filters.
3. Generate an embedding for remaining natural-language intent.
4. Retrieve semantic candidates.
5. Merge and rank.
6. Revalidate offers before displaying or checking out.

11.4 Offer freshness

At checkout time, re-read:
- Current price.
- Inventory.
- Offer status.
- Delivery promise.
- Policy version.

If any material value differs, return PRICE_CHANGED or INVENTORY_CHANGED. Never silently replace an offer after user approval.

11.5 Example ranking

A buyer asks for a laptop below INR 70,000, at least 16 GB RAM, delivery within three days, and best overall value.

The engine may return:
- Offer A: INR 69,999, one day, 16 GB, 10-day return.
- Offer B: INR 64,999, two days, 16 GB, 7-day return.
- Offer C: INR 61,999, five days, 16 GB, 7-day return.

Offer C fails the delivery constraint. The model can explain the trade-off between A and B, but the backend remains the source of truth.

12. PHASE 4 — AGENT ENGINE AND TOOL CONTRACTS
======================================================================

Goal: use AI for interpretation and reasoning while keeping actions bounded.

12.1 Agent loop

1. Receive a user message.
2. Run prompt safety classification.
3. Extract intent.
4. Validate the structured intent.
5. Select an allowlisted tool.
6. Execute the tool through the API service.
7. Return bounded results to the model.
8. Repeat under step and time limits.
9. Produce an answer with decision evidence.
10. Require explicit approval before a consequential action.

12.2 Tools

Read-only tools:
- search_products(intent).
- get_product(product_id).
- get_offer(offer_id).
- compare_offers(offer_ids).
- check_inventory(offer_id).
- get_delivery_options(offer_id).
- get_return_policy(offer_id).
- search_web(query).
- open_url(url).
- extract_page(url).

State-changing tools:
- create_checkout(offer_id, quantity).
- request_authorization(checkout_id).
- create_payment(checkout_id, authorization_id).
- check_payment(payment_id).

The agent should not call provider APIs directly. It invokes application-level tools that enforce permissions and validation.

12.3 Tool schemas

Each tool schema must define:
- Name.
- Description.
- Required parameters.
- Allowed types.
- Maximum lengths.
- Enumerations.
- Authentication requirement.
- Side-effect classification.
- Confirmation requirement.
- Timeout.
- Audit event.

12.4 Tool result format

Use a consistent envelope:

{
  "ok": true,
  "tool": "search_products",
  "request_id": "req_001",
  "data": {},
  "warnings": [],
  "evidence": [],
  "next_actions": []
}

Errors must be structured and deterministic:

{
  "ok": false,
  "error": {
    "code": "OFFER_EXPIRED",
    "message": "The selected offer is no longer valid.",
    "retryable": false,
    "details": {}
  }
}

12.5 Model routing

Route simple tasks to deterministic code or a smaller model:
- Category extraction.
- Unit conversion.
- Product field extraction.
- FAQ lookup.

Route complex tasks to the main model:
- Ambiguous intent interpretation.
- Offer trade-off explanation.
- Tool planning.
- Research synthesis.

The model provider must be abstracted behind an interface:
- generate(messages, tools, settings).
- embed(text).
- moderate(text).

This allows local mocks and provider replacement.

12.6 Prompt Guard

Use a prompt safety classifier before the main agent, but do not treat it as the only defense. Add:
- Input length limits.
- Tool argument validation.
- URL allowlists or safe fetch policies.
- Output schema validation.
- Payment confirmation gates.
- Untrusted-content delimiters.
- No execution of instructions extracted from product text.

13. PHASE 5 — CHECKOUT AND PRICING INTEGRITY
======================================================================

Goal: create a stable purchase object that cannot be changed by model output.

13.1 Checkout creation

Input:
- offer_id.
- quantity.
- delivery option.
- buyer address reference.
- idempotency key.

Server actions:
1. Load the offer.
2. Lock or atomically reserve inventory if required.
3. Validate offer status and expiry.
4. Calculate subtotal.
5. Calculate shipping.
6. Calculate tax according to the demo's explicit assumptions.
7. Apply only configured discounts.
8. Create an immutable price snapshot.
9. Generate price_hash.
10. Persist checkout and audit event.

13.2 Money representation

Use integer minor units. For Indian rupees, store paise. Never use binary floating-point for amounts.

13.3 Price hash

Create a canonical representation of:
- Offer ID.
- Offer version.
- Unit price.
- Quantity.
- Shipping.
- Tax.
- Discount.
- Currency.
- Checkout expiry.

Hash this representation and store it on the checkout. The hash must match before authorization and payment creation.

13.4 Checkout expiry

A checkout should have a short validity window for the demo. On expiry:
- Prevent payment creation.
- Mark the checkout expired.
- Require a fresh offer validation.
- Tell the user that no charge was attempted.

14. PHASE 6 — POLICY, AUTHORIZATION, AND CONSENT
======================================================================

Goal: make spending boundaries explicit and deterministic.

14.1 Policy inputs

- Buyer identity.
- Merchant identity.
- Category.
- Total amount.

15. PHASE 7 — RAZORPAY PAYMENT ADAPTER
======================================================================

Goal: integrate test-mode payments without exposing provider credentials or allowing the AI to bypass controls.

15.1 Adapter boundary

Define a provider-neutral interface:

PaymentProvider.create_order(amount_minor, currency, receipt, notes, idempotency_key)
PaymentProvider.fetch_payment(provider_payment_id)
PaymentProvider.fetch_order(provider_order_id)
PaymentProvider.verify_signature(payload, signature)
PaymentProvider.refund(payment_reference, amount_minor)

The Razorpay adapter implements this interface. A fake provider implements the same interface for tests.

15.2 Create-order sequence

1. Client requests payment for checkout and authorization.
2. API authenticates buyer.
3. Payment service loads checkout.
4. Payment service loads authorization.
5. Validate state, expiry, amount, currency, and price hash.
6. Check idempotency record.
7. Create internal payment attempt.
8. Call Razorpay test API using server-side credentials.
9. Store provider order ID.
10. Return only browser-safe payment data.
11. Record PAYMENT_CREATED.

15.3 Client-side payment

The browser may receive a provider order identifier and public key. It must not receive the secret key. The browser reports the provider response to the server, but the server verifies the signature and independently fetches status where necessary.

15.4 Webhook processing

Webhook endpoint:
- Accept raw request body.
- Read signature header.
- Verify signature using the webhook secret.
- Reject invalid signatures.
- Store provider event ID.
- Ignore duplicate provider event IDs.
- Map provider event to internal payment event.
- Transition the payment state.
- Finalize order only after trusted verification.

15.5 Unknown payment state

If the provider request times out:
- Mark payment as UNKNOWN or PAYMENT_TIMEOUT.
- Do not immediately create another provider order.
- Query provider status using the internal attempt and idempotency key.
- If successful, verify and finalize.
- If failed, expose failure and allow a controlled new attempt.
- If still unknown, place the checkout in manual-review or retryable state.

15.6 Test-mode demonstration

Use a clearly labeled test transaction. The video should show:
- Internal checkout ID.
- Authorization decision.
- Provider order creation.
- Payment response.
- Server verification.
- Order confirmation.
- Audit timeline.

Do not claim a production payment if only test mode is used.

16. PHASE 8 — IDEMPOTENCY, RETRIES, AND FAILURE RECOVERY
======================================================================

Goal: demonstrate production-grade financial behavior.

16.1 Idempotency storage

Create a table with:
- idempotency_key.
- actor_id.
- endpoint.
- request_hash.
- status.
- response_body.
- resource_type.
- resource_id.
- created_at.
- expires_at.

Unique constraint:
- actor_id + endpoint + idempotency_key.

If the same key is reused with a different request hash, return IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_REQUEST.

16.2 Retry policy

Retry only operations known to be safe:
- Read-only catalog queries.
- Provider status queries.
- Webhook processing.
- Non-money background tasks.

For money-mutating calls, retry through the same idempotent operation or first query the previous attempt.

16.3 Failure scenario A: price changed

Initial offer:
- Price INR 64,999.
- Offer version 4.

Before payment:
- Merchant updates price to INR 69,999.
- Offer version becomes 5.

At payment request:
- Server detects version or price hash mismatch.
- No provider payment is created.
- Checkout becomes PRICE_CHANGED.
- Buyer sees: "The approved offer changed before payment, so no charge was made."
- UI offers a fresh comparison and new authorization.

16.4 Failure scenario B: provider timeout

- Server creates one internal payment attempt.
- Provider call times out.
- Payment becomes UNKNOWN.
- Worker queries provider status.
- If captured, verify and confirm order.
- If not found, retain UNKNOWN until bounded retry or manual review.
- Never blindly issue a second charge request.

16.5 Failure scenario C: webhook delay

- Browser reports success.
- Webhook has not arrived.
- Server verifies provider response and fetches provider status.
- Order remains PAYMENT_PENDING until trusted verification.
- UI clearly shows verification in progress.

======================================================================

100 PRODUCTS
  -> ONE MERCHANT
  -> CATALOG API
  -> OFFER ENGINE
  -> CHECKOUT
  -> POLICY
  -> AUTHORIZATION
  -> RAZORPAY TEST PAYMENT

  -> FAILURE RECOVERY

- Semantic retrieval.
- Research agent.
- ACP-like adapter.
- AP2-inspired mandate demonstration.
- MCP tool exposure.
- Dynamic product representation.
- Cross-sell and campaign features.

The strongest positioning is:

"AgentPay is a merchant-side AI commerce gateway that makes products and offers machine-readable, lets AI buyers negotiate and create checkouts, and executes payment only when deterministic policy and authorization checks pass."

The strongest engineering message is not that the system uses a large model. It is that the model is useful but bounded. It can interpret intent, compare valid offers, and coordinate tools, while the commerce core independently controls money, policy, state, identity, inventory, authorization, and verification.

That distinction makes AgentPay feel like merchant infrastructure for agentic commerce rather than a conventional ecommerce website with a chatbot attached.
